# 让音箱播放自建音乐库：设计取舍与踩过的坑

给 [Open-XiaoAI](../../README.md) 的语音助手加一条数据面：说「播放音乐」随机播，
说「播放海阔天空」按歌名点播，说「播放陈奕迅的歌」按歌手播。音乐库侧任意
Subsonic 兼容服务（这里以 Navidrome 为例）。

完整接入步骤见 [`deploy/music/README.md`](../../deploy/music/README.md)，
这里写的是**为什么这么设计**、以及落地时踩过并修掉的坑。

## 架构

```
        ┌────────────────────────────────────────────────┐
        │ connection.py（打了补丁）                      │
说「播放…」→ 有声书匹配（纯文本，快）                  │
        │      ├─ 未命中 → 音乐库解析（搜索接口现查）    │
        │      └─ 命中 → 自己造 tool_call，跳过 LLM      │
        └────────────────────────────────────────────────┘
                              │
                              ▼
                plugins/play_music_library.py
                  提示语入队(TEXT) → 按 id 取音频 → 文件入队(FILE)
                              │
                              ▼
                     TTS 队列 → 桥接 → 音箱 aplay
```

和有声书共用同一条音频通路（服务端既有 FILE 型机制，与自带 `play_music` 同分支），
所以「提示语与音频重叠」「播放期间打断」这两类问题用的是同一套修法。

## 核心设计：搜索即校验

**要不要把整个曲库装进内存做文本匹配？不要。**

有声书只有几十本，可以把书名全量塞进匹配器做纯文本判断。曲库上千首，
而且用户会用歌名、歌手、专辑、甚至半句歌词来点播——全量清单既大又不准
（曲库里同名歌曲多、标签质量参差）。

所以改成把候选词交给音乐库自己的搜索引擎：

- 命中且相似度够高 → 拦截，自己造 tool_call
- 搜不到 → **一律放行**，交回 LLM 正常回答

代价是每次请求多一次本地 HTTP（十几毫秒），换来的是**零误判**：
「播放新闻」搜不到就不会被当成放歌。而漏判只是回到原来的行为（LLM 正常回答），
比误判（音箱突然开始放歌）安全得多。

## 踩过的坑（都有实测证据）

### 1. 接口返回的 `path` 字段是旧值，不能拿它去读本地文件

曲库重排过目录之后，`search3` / `getSong` 返回的 `path` 仍指向**磁盘上不存在**的
旧位置（实测：返回 `Beyond/Beyond - Best Collection/BEYOND.flac`，而磁盘上
只有 `华语音乐/…`）。

但**按 id 流式取回的音频是对的**：实测取回的音频时长 283.56s，与接口自报的
283s 完全吻合。

→ 结论：**用 `stream?id=…` 取音频，不要用 `path` 拼本地路径**。顺带的好处是
容器不需要挂音乐库目录，也就不受挂载/权限/缓存这些问题影响。

### 2. 搜索接口是整串子串匹配，不分词

实测：

| 查询 | 结果 |
| --- | --- |
| `陈奕迅的歌` | 0 条 |
| `陈奕迅 七` | 0 条 |
| `陈奕迅` | 5 条 |

→ 所以「A 的 B」这类说法必须**拆开**再搜：先整串、再尾段（歌名更具体）、再头段（歌手）。

### 3. 一到两个字的候选会搜出完全不相关的东西

实测 `search3("七")` 返回「七年滋养」——子串命中，但不是用户要的那首。

→ 候选词长度 < 2 且非泛化词才拿去搜；单字和纯泛化词一律跳过。

### 4. 泛化判定只能看主候选

「播放陈奕迅的歌」拆开会得到尾段「歌」，如果把每个候选都拿去判是不是泛化词，
尾段「歌」会命中泛化 → 整句被误判成随机播放（这条是实跑测出来的，不是想出来的）。

→ 泛化判定只看**清洗后的整句**。

### 5. 让音乐库转码比原样取回还慢

同一首歌（127MB / 24bit 高码率）：

| 取法 | 耗时 | 文件 |
| --- | --- | --- |
| `format=raw`（原样） | **1.4s** | 127.6MB |
| `format=mp3&maxBitRate=320`（转码） | 5.1s | 13.3MB |

转码省了传输，但把 CPU 花在了服务端——本地网络下传输根本不贵。

→ 默认 `format=raw`，转码作为可选（音乐库不在本机时才值得）。

### 6. 下载的文件不会自动清理

服务端清理临时文件的判断是：

```python
if self.delete_audio_file and tts_file.startswith(self.output_file):
    os.remove(tts_file)
```

而配置里 `output_dir` 是**相对路径** `tmp/`——插件如果传绝对路径
`/opt/xiaozhi-esp32-server/tmp/xxx`，`startswith("tmp/")` 永远是 False，
**文件一个都不会删**，一首歌可能就是上百 MB。

→ 落点用相对路径 `tmp/`（服务端进程 CWD 就是项目根目录），并按
`XIAOZHI_TMP_DIR` 可配；插件另带一个「超过 6 小时还躺着就清掉」的兜底。

### 7. Navidrome 运维侧的两个坑

- **CLI 扫描不更新服务的搜索索引**：`navidrome scan` 只写数据库，正在跑的服务
  用的是它自己扫描时建立的索引。曲目"扫进去了但搜不到/搜到旧路径"时，
  让**服务自己**扫一轮（或重启）才会刷新。
- **`user create` 需要真 TTY**：`docker exec` 不带 `-it` 会失败；而 TTY 会回显
  口令，所以用 `script(1)` 造伪 TTY + 输出按值打码。另外 Navidrome 的 `user`
  表里口令是**可逆加密**存储（Subsonic token 鉴权要明文校验），不能直接写库。
  脚本见 [`nd_create_api_user.sh`](../../deploy/music/nd_create_api_user.sh)。

## 实测时序

单曲 127MB / 24bit 高码率（本地音乐库）：

| 阶段 | 耗时 |
| --- | --- |
| 搜索匹配（请求前） | ~20ms |
| 流式取回音频 | 1.4s |
| 解码成 PCM（服务端自己的链路） | 0.9s |
| 播报提示语 | ~2-3s |

播报正好把取回+解码的 2.3 秒盖住，用户听不到空档。

## 测试覆盖

- **匹配器**（`test_music_intent.py`）：11 条正例（泛化/歌名/歌手/带「的」的说法）
  + 9 条反例（「三体讲了什么」「播放新闻」「帮我把灯关了」等），对着**真实曲库**跑，
  要求正例全命中、反例零误拦。
- **容器内端到端**（`probe_music_in_container.py`）：真 import `core.connection`、
  真查音乐库、真跑 `_merge_tool_calls` 解包、真下载一首并用服务端解码链路解出
  PCM 帧数——不复刻代码，避免掩盖真实的 import 缺失。
